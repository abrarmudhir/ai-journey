# Project Rubric

Use this project rubric to understand and assess the project criteria.

## Set the Stage

| Criteria | Submission Requirements |
| --- | --- |
| Write a Draft PRD | The initial draft of the PRD should include: background information about the industry; the problem you want to solve; and goals and relevant success metrics. |

## Understand

| Criteria | Submission Requirements |
| --- | --- |
| Create “How Might We” stickies | In addition to the pre-existing stickies in the template, create at least eight new stickies. Stickies should ask specific questions following the “How Might We” model. Each sticky should be focused and neither too narrow nor too broad. Each sticky should note a unique idea, although related ideas are acceptable. |
| Pick a primary user type | Identify the primary user you are trying to solve for and explain why you chose that user type. |
| Sort stickies into clusters and themes | Sort stickies into related groups. Duplicate stickies from the student deck should also go into the same group. |
| Select a strategic theme | The selected theme should directly align with the business opportunity and objective. |

## Define

| Criteria | Submission Requirements |
| --- | --- |
| Future Press Release | The review should be told from the customer’s perspective, potentially as a narrative; articulate the problem being solved for the customer; and answer why customers love the product. |
| Define Success Metrics **(Optional)** | The success metrics table includes at least two goals with accompanying signals and success metrics. Goals, signals, and metrics are used correctly. |

## Sketch

| Criteria | Submission Requirements |
| --- | --- |
| Create quick sketches to explore and brainstorm ideas | Include at least eight quick sketches of different ideas. Sketches should be quick and do not need to go into a lot of detail. Sketches should clearly communicate the idea; annotations or captions may be added if helpful. |
| Sketch solutions to depict a more complete idea across the user journey | Include two flows of the potential solution. Each sketch should take about 30 minutes and include: a short title representing the concept; at least three screens; annotations for additional detail; and enough detail to understand how the user progresses through the flow at a high level. |

## Decide

| Criteria | Submission Requirements |
| --- | --- |
| Narrow possible ideas down to a final, single idea to move into the next step | The rationale for the selection should be clear and tie back to specific data, such as size of opportunity and impact, from the Background section of the PRD. |

## Prototype

| Criteria | Submission Requirements |
| --- | --- |
| Create a Storyboard | The storyboard includes at least seven frames that progress in a logical order and include all the steps the user goes through to solve their problem or need. The first frame should start outside of the software and set context around what problem or need the user has and why. The last frame should end outside of the software and show the resolution and impact on the user. At least four frames should relate to the digital experience. Each frame should have a narrative explaining what the user is doing and why. |
| Design a Prototype | The prototype should include at least six screens, feel realistic, leverage UI elements from Apple and Google where appropriate, make sense from a user perspective, and flow correctly forward and backward when applicable. |

## Validate

| Criteria | Submission Requirements |
| --- | --- |
| Write a Research Plan | **Participant selection:** identify the target user for the project and any other characteristics to screen for, such as new versus existing users. **Background questions:** structure questions to build rapport and gain a better understanding of how closely the participant aligns with the target user. **Tasks:** start with a scenario and goal the user is trying to accomplish, then ask follow-up questions to probe specific components of the flow. **General:** maintain a friendly tone, tell the user what to expect, ask open-ended questions, avoid leading questions, and make natural transitions between sections and tasks. |
| Conduct user interview | Conduct at least one user interview. Share notes and the audio recording, and report key findings in the project deck, including what worked well, what did not, and other insights. Recommendations for prioritized changes should include a rationale for each change. |
| List topics for Feasibility Discussion with the Engineering Team **(Optional)** | List specific questions about the feasibility of building the product, including where data is coming from, where data is stored, latency, and other technical challenges. Questions should refer to specific prototype screens whenever possible. |

## Iterate

| Criteria | Submission Requirements |
| --- | --- |
| Update prototype based on feedback from user interviews **(Optional)** | The prototype should retain the same specifications as earlier and implement two high-impact changes from the prioritized changes list developed after the user interviews. |
| Conduct User Interviews **(Optional)** | Conduct at least one more user interview. Share notes and the audio recording, and report key findings in the project deck, including what worked well, what did not, and other insights. |

## Handoff

| Criteria | Submission Requirements |
| --- | --- |
| Add Feature Requirements to PRD | Add detailed requirements for the feature narrative section of the PRD. Give each feature a priority, such as P0, P1, or P2. Requirements should be detailed enough to understand how the feature works and how the user interacts with the product. |

## Suggestions to Make Your Project Stand Out

1. Use additional methods from the lessons to further develop and explore ideas.
2. Organize a digital sprint with other students in the class so you can collaborate in real time through sections 2 and 3 of the project.
3. Include multiple flows in your prototype—for example, a first-time user going through the flow and then the same user returning to the app later to check something.
4. Develop user flows for user types other than the primary user type.
